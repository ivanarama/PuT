## 1. Критические проблемы

### 1.1. ПартииТоваров — ненадёжная идентификация партий

**Файл:** `registers/партии_товаров.yaml`

Измерение `ДатаПоставки` (date) используется для идентификации партий. Если в один день происходит две разных поставки от одного поставщика на один склад, партии сольются в одну.

```yaml
dimensions:
  - name: ДатаПоставки    # ← ненадёжный идентификатор
    type: date
```

**Решение:** Заменить `ДатаПоставки` на `ДокументПоступления` (reference:ПоступлениеТоваров) — уникальная ссылка на документ-основание партии. Дата партии при необходимости извлекается из документа.

---

### 1.2. Регистр ДенежныеСредства — атрибуты-строки вместо ссылок

**Файл:** `registers/денежные_средства.yaml`

Атрибуты `Контрагент`, `Основание`, `Документ` хранятся как строки, а не как ссылки. Это ломает:
- Фильтрацию по контрагенту в отчётах (строковое сравнение GUID)
- Целостность данных (нет FK)
- Авто-JOIN при запросах

```yaml
attributes:
  - name: Контрагент
    type: string          # ← должно быть reference:Контрагент
  - name: Документ
    type: string          # ← должно быть reference на полиморфный документ
```

**Решение:** Перевести на reference-типы. Для `Документ` — добавить `doc_ref` или отдельные ссылки на типы документов.

---

### 1.3. Регистр Взаиморасчеты — строковый атрибут

**Файл:** `registers/взаиморасчеты.yaml`

`ТипКонтрагента` — строка вместо enum. Это может вызвать опечатки и неконсистентность данных.

```yaml
attributes:
  - name: ТипКонтрагента
    type: string          # ← должно быть enum:ВидКонтрагента
```

---

### 1.4. Сборка/Разборка — поле Себестоимость в ТЧ

**Файлы:** `documents/сборка_товаров.yaml`, `documents/разборка_товаров.yaml`

В ТЧ `Расход` и `Приход` хранится поле `Себестоимость`. Согласно принятому решению (memory), себестоимость вычисляется при проведении из регистров, а не хранится в ТЧ. Для других документов это правило соблюдается, но для сборки/разборки — нет.

```yaml
# сборка_товаров.yaml — Расход:
- name: Себестоимость
  type: number            # ← избыточно, должно вычисляться
```

**Решение:** Удалить поля Себестоимость из ТЧ, обновить posting-процедуры для расчёта из ФИФО.

---

### 1.5. Печатные формы Перемещения и Списания — запрос с ошибкой типов

**Файлы:** `printforms/ПеремещениеТоваров/накладная.os`, `printforms/СписаниеТоваров/акт_списания.os`

Фильтр `Склад = &Склад` передаёт строковое представление ссылки, а в регистре `Склад` — reference. Сравнение строки с GUID работает непредсказуемо.

```os
Запрос.УстановитьПараметр("Склад", Строка(Документ.СкладОтправитель)); // ← неправильно
```

**Решение:** Передавать ссылку напрямую: `Запрос.УстановитьПараметр("Склад", Документ.СкладОтправитель);`

---

### 1.6. ПересчётЦен — обработчик ничего не делает

**Файл:** `src/пересчётЦен.proc.os`

Процессор показывает пересчитанные цены (preview), но не записывает их. Пользователь видит изменения, но при закрытии формы всё теряется. Это незавершённая функция.

```os
// Показывает изменения, но не записывает:
Сообщить("Цена: " + ТекЦена + " -> " + НоваяЦена);
// Нет: ЗаписатьЦену(Номенклатура, НоваяЦена);
```

## 2. Логические ошибки и несоответствия

### 2.1. ВозвратОтПокупателя — ФИФО в мягком режиме с фолбэком

**Файл:** `src/возвратотпокупателя.posting.os`

Используется мягкий режим ФИФО (`soft = Истина`) — при отсутствии партий остатков не возникает ошибка, а фолбэк берёт закупочную цену. Это может замаскировать реальную проблему: возврат товара, который не был оприходован (ошибка данных).

```os
Результат = СписатьТоварыФИФО(this.Склад, this.Номенклатура, Колво, this.Дата, Истина); // soft
Если Результат.Сумма = 0 Тогда
    // фолбэк на закупочную цену — скрывает проблему
КонецЕсли;
```

**Решение:** Добавить предупреждение (Сообщить) при фолбэке, чтобы пользователь знал о несоответствии.

---

### 2.2. ВозвратПоставщику — нет проверки на основание

**Файл:** `src/возвратпоставщику.posting.os`

Posting запрашивает партии по `DPostavki` (дата поставки из основания), но не проверяет, что `this.Основание` заполнено. Если основание пустое — запрос вернёт все партии или ничего.

```os
// Основание может быть пустой ссылкой:
Запрос.УстановитьПараметр("DPostavki", this.Основание.Дата); // ← может упасть
```

---

### 2.3. Реализация — неполное снятие резерва

**Файл:** `src/реализациятоваров.posting.os`

Резерв снимается только если указан `this.ЗаказПокупателя`. Если реализация создана вручную (без заказа), но товар был кем-то зарезервирован — складской остаток не учитывает чужой резерв, но и не снимает свой.

```os
Если ЗначениеЗаполнено(this.ЗаказПокупателя) Тогда
    // снимаем резерв
КонецЕсли;
// А если чужой резерв? ПроверитьСвободныйОстаток это учитывает, но сам резерв остаётся
```

---

### 2.4. ПоступлениеТоваров — неконтролируемое снятие ТоваровВПути

**Файл:** `src/поступлениетоваров.posting.os`

При поступлении снимаются товары в пути по ЗаказПоставщику. Не проверяется, что количество поступления не превышает заказанное — можно «снять» больше, чем было заказано.

```os
// Снимаем ТоварыВПути без проверки лимита:
Движения.ТоварыВПути.ВидДвижения = "Расход";
Движения.ТоварыВПути.Количество = Стр.Количество; // может превышать заказ
```

---

### 2.5. ЗаказПоставщику — ОбработкаЗаполнения заполняет сам из себя

**Файл:** `src/заказпоставщику.os`

Функция `ОбработкаЗаполнения` вызывается при вводе на основании `ЗаказПоставщику` — документ заполняется сам из себя, что бессмысленно. Вероятно, должно быть основание на другой документ (например, ЗаказПокупателя для потребности).

```os
Функция ОбработкаЗаполнения(Основание)
    Если ТипЗнч(Основание) = Тип("ЗаказПоставщику") Тогда
        // ← это циклическое основание
```

---

### 2.6. Счёт — отсутствует .os файл формы документа

**Файл:** `src/счёт.os` — **не существует**

У документа Счёт нет серверного модуля формы в src/. Вся логика — только в управляемой форме `forms/счёт/формаобъекта.form.os`. Это создаёт несогласованность: все остальные документы имеют оба файла.

---

### 2.7. ВаловаяПрибыль — отсутствует измерение Склад

**Файл:** `registers/валовая_прибыль.yaml`

Без измерения `Склад` невозможно анализировать прибыль по складам. Для торговой конфигурации это существенный недостаток.

```yaml
dimensions:
  - name: Номенклатура
  - name: Организация
  # ← нет Склад
```

---

### 2.8. ПоступлениеНаРасчётныйСчёт — валидация типа в форме, но не в posting

**Файлы:** `src/поступлениенарасчётныйсчёт.os`, `src/поступлениенарасчётныйсчёт.posting.os`

Форма проверяет `Вид = "БанковскийСчёт"`, но posting-процедура не проверяет. Если документ создан программно (через обработку), проверка обходится.

## 3. Проблемы качества кода

### 3.1. Массовое дублирование функции ПересчитатьИтоги

Функция пересчёта сумм с НДС дублируется **в 7+ формах** (поступлениетоваров, возвратотпокупателя, возвратпоставщику, заказпокупателя, заказпоставщику, реализациятоваров, счёт). Код практически идентичен, отличается только названиями полей.

**Решение:** Вынести в утилиты.module.os функцию `ПересчитатьИтогиТЧ(Документ, СпособУчетаНДС)`.

---

### 3.2. Дублирование парсера 1CClientBankExchange

**Файлы:** `src/загрузкавыписки.proc.os` (362 строки), `forms/загрузкавыписки/формаобъекта.form.os` (385 строк)

Парсер банковской выписки полностью продублирован между CLI-процессором и управляемой формой. Изменение логики в одном месте не отразится в другом.

**Решение:** Вынести парсер в общий модуль (утилиты или отдельный module.os) и вызывать из обоих мест.

---

### 3.3. Монолитный скрипт заполнения демо-данных

**Файл:** `src/заполнитьтестовуюбазу.proc.os` (1061 строка)

Один файл содержит создание всех справочников, документов, проведение, и очистку. При изменении любой сущности файл нужно полностью перепроверять.

**Решение:** Разбить на функции по подсистемам: `СоздатьСправочники()`, `СоздатьЗакупки()`, `СоздатьПродажи()`, `СоздатьКассу()` и т.д.

---

### 3.4. Строковое обёртывание чисел в печатных формах

Во всех печатных формах числа оборачиваются `Строка()`:

```os
Обл.Параметры.Цена = Строка(Стр.Цена);       // "1234.56"
Обл.Параметры.Сумма = Строка(Стр.Сумма);     // "9876.54"
```

**Решение:** Использовать `Формат(Стр.Цена, "ЧДЦ=2")` для единообразного отображения с двумя знаками после запятой.

---

### 3.5. Мёртвый код в печатных формах

**Файл:** `printforms/РеализацияТоваров/накладная.os`

Блок `Иначе` (координатный способ без макета) — это ~40 строк мёртвого кода. Если `Макет = Неопределено`, форма показывает примитивную таблицу вместо реальной накладной.

**Решение:** Удалить fallback-блок или вынести в отдельную утилиту.

---

### 3.6. Неконсистентная обработка ошибок

- Некоторые posting-процедуры выбрасывают `ВызватьИсключение` при ошибках
- Другие используют `Попытка...Исключение` с пустым блоком (молча проглатывают ошибки)
- Особенно критично в печатных формах (Списание, Перемещение) — ошибки запроса скрыты

```os
Попытка
    Запрос = Новый Запрос;
    ...
Исключение
    // ← пустой блок! Ошибка silently проглочена
КонецПопытки;
```

---

### 3.7. Неконсистентное использование функций проверки

- `ПустаяСсылка()` и `ЗначениеЗаполнено()` используются вперемешку
- `Пустая()` и `IsEmpty()` — тоже разные подходы
- Нужно стандартизировать на один вариант

---

### 3.8. Одинаковая логика сборки и разборки без абстракции

**Файлы:** `src/сборкатоваров.posting.os`, `src/разборкатоваров.posting.os`

Обе процедуры — зеркальные отражения с идентичной структурой (ФИФО-списание → распределение себестоимости), но без общей абстракции.

**Решение:** Создать общую функцию `ВыполнитьКомплектацию(Документ, Направление)` в утилитах.

## 4. Архитектурные проблемы

### 4.1. Валюта существует, но не используется

Справочник `Валюта` содержит предопределённые рубль, доллар, евро. Константа `ОсновнаяВалюта = "RUB"`. Но:
- Нет курса валют
- Нет пересчёта в валюту учёта
- Документы всегда в рублях

Это «мёртвый» справочник, создавший ложные ожидания.

---

### 4.2. Нет документа Инвентаризация

Для складской конфигурации отсутствует документ инвентаризации (сравнение фактического и учётного остатка, выявление излишков/недостач). Есть только ручное Оприходование и Списание.

---

### 4.3. Нет документа Корректировка записей регистров

Нет механизма ручной корректировки движений регистров. При ошибке в данных нужно перепроводить документы или писать SQL.

---

### 4.4. Нет статусов документов

Документы не имеют статусов (Черновик, КОплате, Оплачен, Отгружен, Закрыт). Счёт не отслеживает оплату. Заказ покупателя не отслеживает выполнение.

---

### 4.5. Нет пакетных операций

Нельзя:
- Провести/распроводить несколько документов разом
- Массово изменить реквизит
- Создать документы по шаблону

---

### 4.6. Organisation как измерение регистра — избыточность или недоделка

Во всех регистрах `Организация` — измерение. Но в константах `НашаОрганизация` — единственная. Если конфигурация одноз-org — это лишний размер данных и индексов. Если multi-org — функционал не завершён.

---

### 4.7. Нет трассировки проводок

Нельзя от документа перейти к его движениям по регистрам (и обратно). Отсутствует механизм «Откуда взялась цифра».

---

### 4.8. Отчёты без .rep.os скриптов

Только `ВаловаяПрибыль.rep.os` имеет скрипт диаграммы. Остальные 17 отчётов работают только через встроенные запросы в YAML — без сложной логики формирования.

---

## 5. Проблемы безопасности и RBAC

### 5.1. Роль Демо: processors: {} блокирует все обработки

Роль «Демо» имеет полный доступ ко всем документам и справочникам, но `processors: {}` запрещает ВСЕ обработки, включая `ЗаполнитьТестовуюБазу`. Демо-пользователь не может запустить демо-заполнение.

**Решение:** Разрешить как минимум `заполнить_тестовую_базу` для демо-роли.

---

### 5.2. Менеджер не видит документы закупки (кроме чтения)

Менеджер может только читать ПоступлениеТоваров, но не может создать. При этом он может создавать реализации на основании Поступления. Это потенциально создаёт разрыв в бизнес-процессе.

---

### 5.3. Кладовщик не видит ЗаказыПокупателя

Кладовщик не имеет доступа к `ЗаказПокупателя`, но имеет к `РеализацияТоваров` (только чтение). Если отгрузка делается на основании заказа — кладовщик не увидит основание.

---

### 5.4. Нет валидации даты запрета редактирования в posting

Функция `ПроверитьДатуЗапрета` есть в утилитах, но она вызывается из форм (опционально), а не из posting-процедур. Проведение можно сделать задним числом через API.

---

### 5.5. Нет ограничения по организации

Если в системе несколько организаций, нет механизма ограничения видимости документов по организации для конкретного пользователя.

---

## 6. Неполные и заброшенные функции

### 6.1. Scheduled tasks отключены

Оба запланированных задания отключены (`enabled: false`):
- `уведомления_продажи` (ежедневно 18:00)
- `тестовоезадание` (еженедельно)

При этом код уведомлений существует и работает.

---

### 6.2. Уведомления продаж — минимальная реализация

`уведомленияпродажи.proc.os` отправляет простое текстовое письмо с суммами реализаций за день. Нет:
- Вложения (Excel, PDF)
- Группировки по покупателям
- HTML-форматирования
- Настройки получателя (захардкожен в Параметры.Кому)

---

### 6.3. Выгрузка в Excel — базовая реализация

`выгрузкавexcel.proc.os` создаёт простой двумерный массив с ценами. Нет:
- Выбора типа цен для выгрузки
- Форматирования (жирный, цвет)
- Настраиваемых колонок
- Фильтрации по группе номенклатуры

---

### 6.4. Импорт номенклатуры — минимальная валидация

`импортноменклатуры.proc.os` создаёт элементы из JSON, но не проверяет:
- Дубли по наименованию/артикулу
- Обязательные поля (ЕдиницаИзмерения, СтавкаНДС)
- Корректность типов данных

---

### 6.5. РеализацияИзСчёта — не обрабатывает частичную реализацию

`реализацияизсчёта.proc.os` копирует все строки счёта в реализацию. Нет проверки, какие строки уже были реализованы. Повторный запуск создаст дубликат.

---

### 6.6. Акт сверки — есть в YAML отчётов, но нет в подсистемах

Отчёт `акт_сверки.yaml` существует, но не включён ни в одну подсистему (только через ссылки в ролях). Пользователь не увидит его в навигации.

---

## 7. Возможные улучшения

### 7.1. Производительность

| Проблема | Решение |
|----------|---------|
| CAST в каждом виджете для чисел | Ввести числовой тип хранения в платформе (или хотя бы шаблон-хелпер) |
| Нет кэша запросов виджетов | Добавить TTL-кэш для виджетов главной страницы |
| 51 виджет — медленная загрузка | Ленивая загрузка (lazy load) для виджетов ниже первого экрана |
| ФИФО запрашивает ВСЕ партии | Добавить фильтр по дате: только партии до даты документа |

## 8. Перспективные направления развития

### 8.1. Мультивалютный учёт (приоритет: высокий)

**Основа уже есть:** справочник `Валюта`, константа `ОсновнаяВалюта`.

Что нужно:
- Регистр сведений `КурсыВалют` (Валюта + Период → Курс)
- Пересчёт сумм в валюту учёта при проведении
- Отображение в документах в валюте взаиморасчётов
- Отчёт «Валютные переоценки»

**Эффект:** Выход на международный рынок, импорт/экспорт.

---

### 8.2. Документооборот и статусы (приоритет: высокий)

Что нужно:
- Статусная модель документов (Черновик → Согласован → КОплате → Оплачен → Закрыт)
- Маршруты согласования (менеджер → руководитель → кладовщик)
- Уведомления при смене статуса
- История изменений (аудит-след)

**Эффект:** Прозрачность бизнес-процессов, контроль исполнения.

---

### 8.3. CRM-модуль (приоритет: средний)

**Основа:** справочник `Контрагент` с email, телефонами, контактным лицом.

Что нужно:
- Сделки (воронка продаж)
- История взаимодействий (звонки, встречи, письма)
- Автоматическая сегментация клиентов
- Напоминания о контактах

**Эффект:** Управление продажами, удержание клиентов.

---

### 8.4. Автозаказ и управление запасами (приоритет: средний)

**Основа:** `МинимальныйОстаток` в номенклатуре, `ТоварыВПути`, `РезервыТоваров`.

Что нужно:
- Обработка «Формирование заказов по минимуму»
- Учёт срока поставки от поставщика
- Сезонные коэффициенты
- ABC/XYZ анализ для приоритизации

**Эффект:** Снижение неликвидов, предотвращение дефицита.

---

### 8.5. Мобильная торговля (приоритет: средний)

**Основа:** REST API платформы OneBase.

Что нужно:
- Мобильные формы: сбор заказов, инвентаризация, отгрузки
- Офлайн-режим с синхронизацией
- Сканирование штрихкодов камерой
- GPS-трекинг торговых представителей

**Эффект:** Автоматизация «поля», рост продаж.

---

### 8.6. Интеграции (приоритет: средний)

**Основа:** HTTP-функции DSL (`httpget`, `httppost`), email (`ОтправитьПисьмо`).

Что нужно:
- Интеграция с маркетплейсами (Wildberries, Ozon)
- Интеграция с банками (Сбербанк, Тинькофф API)
- Синхронизация с бухгалтерией (1С:Бухгалтерия)
- Webhook-уведомления во внешние системы

**Эффект:** Исключение двойного ввода, автоматизация.

---

### 8.7. Аналитика и BI (приоритет: низкий)

**Основа:** 51 виджет, подсистема графиков.

Что нужно:
- Конструктор отчётов (drag-and-drop)
- Предиктивная аналитика (тренды, прогнозы)
- Кастомизируемые KPI-дашборды по ролям
- Экспорт отчётов в PDF/Excel по расписанию

**Эффект:** Управленческие решения на основе данных.

---

### 8.8. Бюджетирование (приоритет: низкий)

Что нужно:
- Документ «Бюджет» (план доходов/расходов)

- Лимиты расходов по подразделениям
- Финансовое планирование (кассовый разрыв)

**Эффект:** Финансовая дисциплина, контроль расходов.

---

### 8.9. Производство (приоритет: низкий)

Что нужно:

**Эффект:** Полный цикл от закупки до производства и продажи.
