## ✅ Сделано: 3 блокирующие ошибки `onebase check`

Все три имели один корень — **авто-JOIN presentation на измерение-ссылку типа
«документ» у виртуальной таблицы `.Остатки()`**. Платформа для презентации ссылки
подставляет `наименование`, но у документа его нет (презентация = Номер+Дата) →
`SQL logic error: no such column: ref_заказпоставщику.наименование`.

Автор уже знал про баг и обошёл его в коде (`src/утилиты.module.os:200-202`,
функция `ЧужиеРезервыПоСкладу` — комментарий «автоджойн платформы ищет
наименование у документа, которого нет»), но в трёх декларативных запросах нет.

| Файл | Измерение-документ |
|---|---|
| `reports/товары_в_пути.yaml` | `ЗаказПоставщику` |
| `reports/резервы_товаров.yaml` | `ЗаказПокупателя` |
| `widgets/ожидаемые_поставки.yaml` | `ЗаказПоставщику` |

**Применённый фикс** (повторяет рабочий паттерн `reports/оплаты_реализаций.yaml`):
запрос к **базовой** таблице регистра вместо `.Остатки()`, ручная агрегация
остатка через `СУММА(ВЫБОР КОГДА вид_движения = "Приход" ТОГДА … ИНАЧЕ -… КОНЕЦ)`,
фильтр периода `period <= &НаДату`, **алиас регистра + квалификация всех колонок**
(снимает вторичную ошибку `ambiguous column name: склад_id` — авто-JOIN на
документ-заказ тянет его собственный `склад_id`), отбор `ИМЕЯ … > 0`.

Пример (товары_в_пути):
```
ВЫБРАТЬ
  Т.Номенклатура КАК Номенклатура,
  Т.Склад КАК Склад,
  Т.ЗаказПоставщику КАК ЗаказПоставщику,
  СУММА(ВЫБОР КОГДА Т.вид_движения = "Приход" ТОГДА Т.Количество ИНАЧЕ -Т.Количество КОНЕЦ) КАК Количество,
  СУММА(ВЫБОР КОГДА Т.вид_движения = "Приход" ТОГДА Т.Сумма ИНАЧЕ -Т.Сумма КОНЕЦ) КАК Сумма
ИЗ РегистрНакопления.ТоварыВПути КАК Т
ГДЕ (&НаДату ЕСТЬ ПУСТО ИЛИ Т.period <= &НаДату)
  И (&Склад ЕСТЬ ПУСТО ИЛИ Т.Склад = &Склад)
СГРУППИРОВАТЬ ПО Т.Номенклатура, Т.Склад, Т.ЗаказПоставщику
ИМЕЯ СУММА(ВЫБОР КОГДА Т.вид_движения = "Приход" ТОГДА Т.Количество ИНАЧЕ -Т.Количество КОНЕЦ) > 0
УПОРЯДОЧИТЬ ПО Т.Номенклатура, Т.Склад
```

> Это **обход**. Системно правильнее — починить движок (документ должен
> авто-презентоваться через Номер+Дата при выборке измерения из `.Остатки()`).
> Кандидат на engine-level issue.

## 🔴 Критичное

### A1. Роли не синхронизированы с новыми документами  *(пересекается с анализ_проекта 5.2–5.3, но расширено новыми документами)*

Подсистемы показывают документы, но роли не дают их открыть (allow-list:
отсутствие в `documents` = запрет, что подтверждается семантикой `processors: {}` = «запретить все»).

| Роль | Файл | Чего не хватает |
|---|---|---|
| Менеджер | `roles/менеджер.yaml` | `ЗаказПокупателя`, `ВозвратОтПокупателя` (подсистема «Продажи» их показывает; `РеализацияТоваров` заполняется на основании заказа — `src/реализациятоваров.os:2`) |
| Снабженец | `roles/снабженец.yaml` | `ВозвратПоставщику` |
| Кладовщик | `roles/кладовщик.yaml` | `СборкаТоваров`, `РазборкаТоваров`, `ВозвратОтПокупателя`, `ВозвратПоставщику` |
| Демо | `roles/демо.yaml` | 6 документов (Заказы, Возвраты, Сборка, Разборка) + отчёты `ТоварыВПути`, `РезервыТоваров`, `СвободныеОстатки`, `Неликвиды` — демо не показывает половину функционала |

**Решение:** добавить недостающие документы/отчёты в `permissions` каждой роли
(с правами `[read, write, post, unpost]` для исполнителей роли).

### A2. `widgets/средний_чек.yaml:25` — неверный знаменатель  *(новое)*

```
CAST(СУММА(Выручка) / КОЛИЧЕСТВО(*) AS INTEGER) КАК Значение
```
`КОЛИЧЕСТВО(*)` считает строки регистра `ВаловаяПрибыль` = **позиции номенклатуры**
во всех продажах (одна строка на товарную строку, см. `src/реализациятоваров.posting.os:53`),
а не число чеков. Средний чек занижен в разы (продажа из 5 строк = 5 «чеков»).
Плюс деление на ноль при отсутствии продаж за период.

**Решение:** делить на число документов-регистраторов:
`СУММА(Выручка) / КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Регистратор)` (и защита от нуля).

### A3. `widgets/товары_к_заказу.yaml:24,29,31` — нарушение правила `AS INTEGER`  *(новое)*

```
CAST(Н.МинимальныйОстаток AS INTEGER) КАК Минимум,
CAST(COALESCE(СУММА(Д.КоличествоОстаток), 0) AS INTEGER) КАК Остаток
...
ГДЕ CAST(Н.МинимальныйОстаток AS INTEGER) > 0
ИМЕЯ COALESCE(СУММА(Д.КоличествоОстаток), 0) < CAST(Н.МинимальныйОстаток AS INTEGER)
```
AGENTS.md прямо требует для сырого числового поля `CAST(... AS NUMERIC)`, **не**
`AS INTEGER` («усекает дробь»). Здесь усечение применяется к **порогу дозаказа** в
сравнении — при дробном минимуме/остатке (кг, л) порог считается неверно.

**Решение:** заменить `AS INTEGER` → `AS NUMERIC` для `Н.МинимальныйОстаток`;
агрегат `СУММА(Д.КоличествоОстаток)` не кастить вовсе (он уже числовой).

## 🟡 Систематическое (технический долг)

### B1. `CAST(СУММА(...) AS INTEGER)` в ~30 виджетах  *(анализ_проекта 7.1 — но там как «производительность», здесь как корректность отображения)*

Усекает копейки **вниз** вместо округления; по AGENTS агрегаты `СУММА()` кастить
не нужно. Для KPI-плашек это сознательное «убирание копеек», но даёт нисходящее
смещение (1999.99 → 1999). Затронуты: `топ_поставщики`, `топ_покупатели`,
`касса_остаток`, `денежный_поток`, `выручка_месяца`, `валовая_прибыль_kpi` и др.

**Решение:** `ОКР(..., 0)` для округления вместо усечения, либо убрать CAST и
форматировать на уровне колонки (`format: number`).

      В скриптовом DSL (вне запроса) `Окр` работает. Несогласованность наборов функций
      между запросом и скриптом. Ср. с уже известным `ЦЕЛ`→CAST/ROUND.
