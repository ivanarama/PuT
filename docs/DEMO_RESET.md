# Ночное обновление демо

Старый `onebase run --demo-backup ...` восстанавливал архив буквально, вместе со старыми датами и конфигурацией. После восстановления генератор не запускался, поэтому текущий месяц со временем пустел.

В PuT 1.3.0 ночное обновление восстанавливает согласованную PostgreSQL-копию, загружает текущую конфигурацию и заново проводит документы относительно сегодняшней даты. Затем независимо проверяет продажи и выручку текущего месяца. Нулевой результат завершает операцию с ошибкой. `ОпорнаяДата` обработки служит для воспроизводимых тестов; ночной сценарий её не передаёт.

С версии 1.3.3 заполняются также 14 примеров этапов заказов: по одному для каждого этапа покупателя и поставщика. Проверка ночного обновления отклоняет неполное или дублированное покрытие. На стандартном наборе получается 10 заказов покупателей, 9 поставщикам, 7 реализаций и 5 поступлений. Дополнительная приёмка и отгрузка исполняют завершённые заказы, документы закрытия снимают обеспечение отменённых. Повторный запуск заполнения без «Очистить» добавляет только отсутствующие примеры и сохраняет прежние документы.

## Локальная проверка SQLite

```powershell
python scripts/reset_demo.py --onebase .local/onebase-preview.exe --sqlite .local/demo-check.db --demo-only
```

Скрипт удаляет все документы указанной демобазы. Рабочие базы для него не подходят. Справочники и пользователи при локальном запуске сохраняются.

## PostgreSQL на Orange Pi

Старая база `demo` содержит устаревшие текстовые колонки дат и ссылок. Для 1.3.0 создаётся отдельная база `put_demo_130` с актуальной схемой; учётные записи переносятся из прежней базы. Старая база остаётся для отката. Служба и адрес PuT сохраняются, общий бинарь остальных приложений не меняется.

Ночной сценарий использует **нативный `pg_dump -Fc`**, а не универсальное восстановление `.obz`: проверка старого формата обнаружила несовместимые типы, а универсального v2 — ошибку восстановления JSON-констант. Флаг `--baseline` у общего `reset_demo.py` поэтому отказывает до обращения к базе. PostgreSQL обслуживает `scripts/reset_demo_postgres.py`.

Порядок обновления:

1. Остановить `onebase.service`; убедиться, что других клиентов нет.
2. Сохранить полную текущую базу и отдельную копию таблиц пользователей, ролей, сессий и резервных кодов 2FA.
3. Восстановить нативный демо-архив в изолированную базу. Вернуть актуальные учётные записи и бинарные файлы демо.
4. От имени `onebase` загрузить текущую конфигурацию, очистить и заново заполнить документы.
5. Проверить продажи, выручку и сохранение пользователей. При ошибке восстановить полную копию, сделанную перед сбросом.
6. Поднять сервер; ошибку оставить в журнале systemd.

Сценарий принимает только локальную PostgreSQL и имена `put_demo_<версия>` / `put_release_<версия>`. Он проверяет сборку платформы, архив и отсутствие клиентов до замены базы, а файловая блокировка исключает одновременные сбросы. Он требует `--demo-only`. Административная часть выполняется root через PostgreSQL-пользователя `postgres`; прикладной код запускается под `onebase`.

Пути поставки:

- `/opt/onebase-put/current/onebase` и `current/project` — бинарь и конфигурация текущего релиза.
- `/opt/onebase-put/demo.dump` — проверенный нативный архив актуальной схемы.
- `/opt/onebase-put/baseline-files` — бинарные файлы этого архива.
- `/var/lib/onebase-put/files` — рабочее файловое хранилище, `ONEBASE_FILES_DIR`.
- `/opt/onebase-put/backups` — копии перед обновлениями и сбросами; доступ только root.
- `/etc/onebase/put-demo.env` — `DATABASE_URL` и `ONEBASE_FILES_DIR`, права 0600.

`scripts/systemd/put-demo-reset.service` останавливает и поднимает сервер. `put-demo-reset.timer` запускается ежедневно в 02:00 по часовому поясу сервера. У основной службы должен быть убран `--demo-backup`, чтобы два механизма не конкурировали. Бинарь, конфигурация и root-сценарий принадлежат root; рабочее файловое хранилище — `onebase`.

Перед включением таймера дважды прогоните сценарий на отдельной PostgreSQL: число документов не должно расти, пользователи должны сохраняться, продажи и выручка месяца — оставаться положительными. Нативный архив и его файлы готовятся из этой проверенной схемы. Для диагностики: `systemctl status put-demo-reset.timer`, `journalctl -u put-demo-reset.service`.
